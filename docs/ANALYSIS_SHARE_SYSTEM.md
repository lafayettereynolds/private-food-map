# Taste Map 分析页与分享海报系统

更新时间：2026-08-26

## 目标

分析页负责完整阅读，分享海报负责对外传播。两者使用同一份 `AnalysisShareData`，但不直接截取页面，也不共享页面布局。

当前支持六类分析：

- `TASTE_PROFILE`：完整口味档案
- `COMPANION_ANALYSIS`：饭搭子分析
- `RECOMMENDATION_SOURCE`：推荐来源分析
- `MONTHLY_REVIEW`：本月回味
- `ANNUAL_REVIEW`：年度回味
- `ON_THIS_DAY`：那年今日

## 数据与渲染流程

```text
Restaurant / Visit / Profile 等现有数据
  → AnalysisShareService 构建统一 AnalysisShareData
  → Privacy Filter 移除不可分享字段
  → FoodVisualResolver 选择真实且匹配的视觉素材
  → AnalysisPosterRenderer 生成独立 1080 × 1440 海报
  → AnalysisShareSheet 预览、换图、保存图片或系统分享
```

`AnalysisShareService` 只生成可验证的标题、结论、指标、洞察和代表餐厅证据，不在组件中拼接分析事实。页面与海报都消费服务层结果，后续 iOS 可以复用同一数据契约。

## 图片选择

主视觉按以下顺序降级：

1. 当前分析范围内的 Visit 实拍
2. 代表餐厅的稳定封面
3. 合法 Provider 提供的餐厅图片
4. 与菜系相关的内置兜底图

选择结果使用用户、分析类型和统计周期生成稳定种子。同一报告重复打开保持一致，不同周期或不同用户可产生不同选择。“换一张照片”只在当前报告真实候选池内轮换，不会注入无关的随机美食图片。

代表餐厅卡片中的图片以 `restaurantId` 绑定，名称、图片和说明必须来自同一家餐厅。

## 海报布局

- 固定导出尺寸：1080 × 1440，3:4。
- 使用 Taste Map 官方北极熊汉堡图标、品牌蓝、暖灰背景和克制的编辑式排版。
- 每张海报只保留 5–8 个最重要结论，不复制完整分析页，也不使用后台仪表盘式密集卡片。
- 各分析类型拥有不同标题与重点，但复用同一渲染器、视觉解析和隐私规则。

## 隐私规则

分享数据默认经过严格过滤：

- 不包含邮箱、内部账号 ID、精确私人地址或可识别的私人位置。
- 不包含真实消费金额，除非未来存在明确的用户分享授权。
- 饭搭子默认使用可分享昵称或匿名表达，不泄露对方私密数据。
- 只使用可公开的餐厅证据和当前用户有权限分享的图片。
- 不为了填满海报编造 AI 结论、餐厅事实或样本数据。

推荐来源海报中的人物来源是当前用户自己记录的推荐来源，因此保留其当前显示名称；不携带对方账号 ID、私人资料、笔记或消费。顶部最多展示“最懂我 / 最容易种草 / 最稳定 / 最坑”四项，其中“最坑”只有在至少 6 家独立有评分餐厅达到门槛时出现，并使用轻微暖色强调，不使用警报红。

## Web 与 iOS

Web 当前使用 SVG/Canvas 兼容的运行时渲染生成 PNG，并调用 Web Share API；浏览器不支持文件分享时自动降级为保存 PNG。

iOS UI 和原生渲染器本轮未开发。后续可复用 `AnalysisShareData`、隐私过滤结果、稳定视觉标识和 1080 × 1440 版式契约，在原生端实现等价渲染。

## 数据结构与迁移

海报在运行时生成，不持久化新的报告表、图片缓存表或分析快照。本轮没有修改 IndexedDB、D1 Schema 或同步协议，因此没有新增或执行 migration。

## 验证范围

- 六类分析页均有可用分享入口。
- 海报预览可生成，主图可在真实候选池内切换。
- PNG 可保存；支持文件分享的浏览器可调用系统分享。
- 代表餐厅图片与名称保持对应。
- 同一报告选图稳定，不同周期能轮换。
- Visit 实拍和餐厅封面的优先级正确。
- 官方 App 图标进入海报。
- 隐私字段不会进入分享数据。
- 推荐来源的人物名称保持真实且随改名更新；小样本不会生成“最坑”卡片或分享结论。
- 1080 × 1440 导出尺寸和非页面截图式布局通过自动测试。

## 当前限制

- 暂未生成二维码。
- 暂无持久化海报缓存，每次由当前数据实时生成。
- 系统分享能力取决于浏览器对文件型 Web Share API 的支持。
- iOS 原生海报渲染、系统相册权限和原生分享面板需在后续 iOS 客户端中实现。
