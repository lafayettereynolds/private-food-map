# Taste Map 分析页与分享海报系统

更新时间：2026-09-05

## 目标

### 2026-09-07 本人完整画报与对外分享预览

`画报`首先展示同一报告的本人完整预览，口味档案保留消费、人均和结构化同行
场景；它不是可直接导出的分享载荷。点击`预览分享版`先生成并显示脱敏版本，
用户再次点击`分享画报`才导出当前预览的同一 Blob。Browser 保存入口仅在分享
预览显示，不新增本人完整版下载或照片导出权限。隐私过滤后的空区域明确说明，
不把它们呈现为零值图表。

五类数据页和画报的重点发现通过 `analyticsReportHighlights` 使用同一优先级、
样本状态与结果行。完整文字分享继续保留所有可分享结果，不被画报的篇幅限制。
只有日期的历史记录保留在总次数，但不进入时段比例；两种展示都标明时段覆盖。
本次参考图沿用口味档案 1080 × 1620，不采纳文字参考中统一 9:16 的建议。

### 2026-09-06 当前用户指令覆盖

Hybrid 的数据模式改为手机可读的纵向完整报告，画报仍为独立固定尺寸分享摘要。
入口统一使用 `analyticsReport.ts`；数据页和 `analyticsReportShare.ts` 只消费同一份
owner／周期／饭搭子或来源选择快照，不在组件内另算统计。历史月份／年份可以选择。
两种模式保留顶部分享按钮；图片分享使用预览已生成的同一个 Blob，过期异步结果不回填。
默认分享隐藏个人消费、私人笔记和同行人姓名，并检查本人照片的导出授权及归属。
文本分享保留所有可分享板块和评分；固定尺寸画报明确为摘要，不代替完整数据报告。
这次仅改现有只读分析与投影，不改变数据库和用户历史记录。

分析页负责完整阅读，分享海报负责对外传播。两者使用同一份 `AnalysisShareData`，但不直接截取页面，也不共享页面布局。

当前支持六类分析：

- `TASTE_PROFILE`：完整口味档案
- `COMPANION_ANALYSIS`：饭搭子分析
- `RECOMMENDATION_SOURCE`：推荐来源分析
- `MONTHLY_REVIEW`：本月回味
- `ANNUAL_REVIEW`：年度回味
- `ON_THIS_DAY`：那年今日

## 数据与渲染流程

```text
Restaurant / Visit / Profile 等现有数据
  → AnalysisShareService 构建统一 AnalysisShareData
  → Privacy Filter 移除不可分享字段
  → FoodVisualResolver 选择真实且匹配的视觉素材
  → AnalysisPosterRenderer 生成独立海报
  → AnalysisShareSheet 预览、换图、保存图片或系统分享
```

`AnalysisShareService` 只生成可验证的标题、结论、指标、洞察和代表餐厅证据，不在组件中拼接分析事实。页面与海报都消费服务层结果，后续 iOS 可以复用同一数据契约。

## 图片选择

主视觉按以下顺序降级：

1. 当前分析范围内的 Visit 实拍
2. 代表餐厅的稳定封面
3. 合法 Provider 提供的餐厅图片
4. 与菜系相关的内置兜底图

选择结果使用用户、分析类型和统计周期生成稳定种子。同一报告重复打开保持一致，不同周期或不同用户可产生不同选择。“换一张照片”只在当前报告真实候选池内轮换，不会注入无关的随机美食图片。

代表餐厅卡片中的图片以 `restaurantId` 绑定，名称、图片和说明必须来自同一家餐厅。

## 海报布局

- `TASTE_PROFILE` 固定导出 1080 × 1620（2:3），完整复刻已确认的编辑式口味档案结构：统计周期、中央菜系关系图、数据总览、最常吃 TOP 3、口味偏好、近期洞察、消费分布、人均消费区间、城市足迹、常见饭搭子和用餐时间偏好。
- 其余四类分析海报继续使用 1080 × 1920（9:16），不得为了统一外观而复制口味档案的内容结构。
- 使用 Taste Map 官方北极熊汉堡图标、品牌蓝、暖灰背景和克制的编辑式排版。
- 口味档案页面与分享图使用同一份真实数据快照和同一模块顺序；分享图是独立 Renderer 输出，不是页面截图或另一套简化模板。
- 各分析类型拥有不同标题与重点，但复用同一渲染器、视觉解析和隐私规则。
- 菜系、口味、环境/场景信号分开统计；用户可见评分一律为 10 分制，不使用虚构数字补齐版面。
- 分享海报预览必须留在当前页面内直接缩放：双指张合可在 75%–500% 范围查看，放大后可拖动，双击恢复完整尺寸；关闭、保存和系统分享控件不随海报缩放。

## 隐私规则

分享数据默认经过严格过滤：

- 不包含邮箱、内部账号 ID、精确私人地址或可识别的私人位置。
- 不包含真实消费金额，除非未来存在明确的用户分享授权。
- 饭搭子默认使用可分享昵称或匿名表达，不泄露对方私密数据。
- 只使用可公开的餐厅证据和当前用户有权限分享的图片。
- 不为了填满海报编造 AI 结论、餐厅事实或样本数据。

推荐来源海报中的人物来源是当前用户自己记录的推荐来源，因此保留其当前显示名称；不携带对方账号 ID、私人资料、笔记或消费。顶部最多展示“最懂我 / 最容易种草 / 最稳定 / 最坑”四项，其中“最坑”只有在至少 6 家独立有评分餐厅达到门槛时出现，并使用轻微暖色强调，不使用警报红。

## Web 与 iOS

Web/Hybrid 当前使用 SVG/Canvas 兼容的运行时渲染生成 PNG，并调用 Web Share API 或 iOS 系统分享；浏览器不支持文件分享时自动降级为保存 PNG。

## 数据结构与迁移

海报在运行时生成，不持久化新的报告表、图片缓存表或分析快照。本轮没有修改 IndexedDB、D1 Schema 或同步协议，因此没有新增或执行 migration。

## 验证范围

- 六类分析页均有可用分享入口。
- 海报预览可生成，主图可在真实候选池内切换。
- PNG 可保存；支持文件分享的浏览器可调用系统分享。
- 代表餐厅图片与名称保持对应。
- 同一报告选图稳定，不同周期能轮换。
- Visit 实拍和餐厅封面的优先级正确。
- 官方 App 图标进入海报。
- 隐私字段不会进入分享数据。
- 推荐来源的人物名称保持真实且随改名更新；小样本不会生成“最坑”卡片或分享结论。
- 口味档案 1080 × 1620、其他分析 1080 × 1920 的导出尺寸和非页面截图式布局通过自动测试。
- Native 与 Hybrid 海报预览均支持原页放大、缩小和放大后的拖动；缩放不会改变最终导出图片，也不会移动保存、分享控件。

## 当前限制

- 暂未生成二维码。
- 暂无持久化海报缓存，每次由当前数据实时生成。
- 系统分享能力取决于浏览器对文件型 Web Share API 的支持。
- 正式应用当前通过 Hybrid renderer 生成口味档案海报，并交给原生系统分享面板。
