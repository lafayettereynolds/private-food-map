# Taste Map 产品与技术决策

更新时间：2026-08-25

- App 启动后首先显示地图；地图与列表采用两个完整模式，地图模式仍保留餐厅分类栏和始终可见的“查看列表”入口。
- “味觉足迹”是列表模式中的独立动态流，不是地图筛选；按 Visit 时间展示笔记与照片，并允许持续滚动浏览。
- 当前位置使用“圆形头像 + 主色外圈 + 小尖角”的定位气泡；餐厅继续使用圆形图片标记，两个体系不混用。
- 全局视觉只使用一套 Token：主品牌色 `#506C8C`、深品牌色 `#344F69`、浅品牌背景 `#EDF2F6`、主文字 `#172A3A`、次文字 `#727C84`、页面背景 `#F7F7F5`、卡片 `#FFFFFF`、分割线 `#E3E6E8`、未选中 `#7C7C78`和低频暖色 `#D09A63`；页面不再各自写死近似蓝灰色。
- 北极熊汉堡是 Taste Map 统一应用图标，同时用于页内品牌标识、favicon、PWA/手机桌面图标和 Windows 启动快捷方式。
- 表单中的可选附加项用明确动作入口表达：菜品直接显示“添加”，饭搭子默认限量展示并通过“更多”展开。
- “适合场景”描述单次 Visit，允许同时选择多个场景并可自定义；旧单值字段只用于兼容。
- 单次到访不单独管理可见性；用户在“我的”中统一选择仅自己、互相关注或公开。
- 关注关系只在个人页显示“关注我的”和“我关注的”；互相关注作为“我关注的”列表状态，不单独设入口。
- “今天吃什么”转盘属于“我的”中的工具模块，不占独立底部导航入口；地图餐厅只加入统一候选池，不自动打开轮盘。
- 转盘候选餐厅属于当前会话临时状态，不写入餐厅/到访数据；最多 10 家。轮盘固定以至少 5 个视觉分区呈现，真实候选才会参与随机，空位只作为“添加更多餐厅”入口；只有用户主动开始才旋转并播放可静音的持续提示音。
- 底部主导航只保留地图、发现和我的；“添加餐厅”作为独立快捷按钮悬在发现入口正上方，不占用导航栏位。
- “发现”的五栏数据逻辑独立：关注看已关注用户；为你推荐只依据自己的历史记录推荐餐厅；同味之选依据口味相似用户；最新按时间；趋势按 7/30 天热度。
- “为你推荐”的解释必须指向用户曾吃过的具体相似餐厅并给出相似百分比，不能用笼统的“经常给某菜系高分”。
- “为你推荐”和地图推荐的距离筛选支持 1/3/5/10 公里和按最近排序。设备城市与浏览城市一致时使用设备位置；跨城市或无定位权限时改用当前浏览城市候选中心并明确显示锚点，禁止静默使用异地 GPS。距离、评分属于硬筛选，系统只建议最小有效放宽，必须由用户点击后才改变条件；排序不计入筛选数量，也不得减少候选。
- 推荐空状态统一区分筛选归零、推荐证据不足、无公开内容、无关注动态与趋势样本不足；筛选归零由运行时 Filter Result Resolution 从同一候选池分析原因和放宽建议，不持久化、不新增数据库字段。
- 测试发现数据只允许写入 Development 本地 D1；Production 不自动生成、复制或清理测试用户。
- 餐厅社交评分按用户等权：先计算每个用户在同一餐厅的个人平均，再计算全部用户、好友和口味相似人群平均；当前餐厅详情不展示重复到访率。
- 餐厅评分参考固定为历史预测、全部用户、好友评分和同味评分四项：大圆显示分数，小圆显示历史餐厅样本数或参与用户数；历史预测动态使用本地有效评分、菜系标签、价位、城市与重复到访相似度计算，不写入数据库、不伪造无样本分数。
- 餐厅详情保留三枚明确快捷动作“去过 / 想吃 / 抽签”，并放在店名右侧以节省纵向空间；信息顺序固定为评分参考、用户实拍、我的到访概览、到访历史。公开发现记录中的实拍必须进入同一详情的用户实拍区，不能只在发现卡片出现。
- 评分参考的大圆按 10 分制评分色阶显示；小圆只显示数字样本量，不追加“家/人”。无数据时圆内只显示统一空状态图案与“暂无数据”，不在圆外重复说明。
- 去过餐厅的顶部信息必须明确显示当前用户自己的 10 分制评价；个人评价与全部用户、好友、同味评分保持独立层级。
- “附近餐厅”必须来自浏览器高精度 GPS，并先转换为高德坐标，再并行使用多个餐饮关键词检索 3 公里范围、去重并按真实距离排序；没有可靠定位时不使用城市级结果冒充附近结果。
- 地图列表、发现页点击餐厅都在当前上下文展示完整餐厅信息，不通过切回地图表达详情；移动端详情覆盖地图内容。
- 个人资料、头像和地图隐私收进同一个“编辑资料与隐私”面板；关注管理与用户发现分开呈现。
- 免费用户可使用全部预设头像；只有服务端确认的会员可上传自定义头像，客户端不能自行提升会员等级。
- Web 仍是当前主要客户端，但数据模型、同步接口、认证与图片引用不得绑定到特定 Web UI，以便未来 iOS 复用。
- 只有字段、数据库结构或同步协议变化时才检查 migration；纯 UI、布局、颜色和文案修改跳过数据链路检查。
- Restaurant 的跨平台身份由 Global Restaurant ID / Provider 映射服务维护；地图 SDK 的 POI ID 只是来源标识，不能成为所有业务模型的唯一真值。
- 同步采用 local-first：本地写入先成功，随后由幂等操作队列增量上云；图片只同步元数据和存储引用，不把二进制写入 D1。
- 会员能力以服务端有效 Entitlement 为准；前端开关和本地字段不能直接授予会员权限，管理员变更必须留下审计记录。
- 评分允许缺省；填写评分时使用半星，存储仍为 0.5—5 星，展示和统计统一换算为 10 分制。
- 推荐、口味档案、餐厅统计和月报/年报共享“有效 Visit”口径；重复同步、软删除和未评分记录按各指标定义排除。
- 个性化推荐只依据当前用户的历史偏好；同味推荐才使用相似用户行为；数据不足必须显示真实降级原因，不能伪造推荐或 0 分。
- 食单是独立的内容组织实体，不等同于想吃；公开食单使用 `#list=<id>` 稳定地址，服务端按 private/friends/public 校验读取权限。
- 食单、地图列表和发现页的餐厅点击都在当前上下文打开同一套完整餐厅详情；关闭详情恢复来源页面、原食单及原来的发现分栏。
- 月报和年鉴动态计算，不复制保存一份容易过期的统计结果；对外分享必须使用去隐私摘要，默认不包含真实支出、饭搭子、推荐来源或私人照片。
- 饭搭子分析的事实来源默认仅为当前用户自己的 Visit：消费只统计 `myActualSpend`，评分只描述“和 TA 一起时我的评分”，绑定用户在没有明确可见权限时也不读取其 Visit 或 TasteProfile；解绑只移除账号关联，不删除历史饭搭子和到访。
- 饭搭子洞察统一按共同 Visit 数量分级：0–2 次仅显示事实总览，3–5 次允许基础分析，6 次以上才显示完整关系洞察；页面不得把普通饭搭子包装为排行榜、共同评分或关系强弱判断。
- 推荐来源按 Restaurant acquisition source 归因：同一餐厅只归入最早一条带来源的有效 Visit，一家餐厅只贡献一个推荐样本；后续 Visit 仅用于该餐厅的个人平均评分、重复到访和实际消费结果验证。历史来源缺失保持未知，不从笔记或平台信息猜测。
- 推荐来源分析是当前用户私有的结果检验，不生成来源的全局“可靠度”；Taste Map 自己的推荐与好友、平台和自行发现使用同一口径。来源表现可以形成受样本置信度控制的弱推荐信号，但不能凌驾于预算、距离、场景、营业状态和长期 TasteProfile。
