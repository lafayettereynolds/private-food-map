# Taste Map 产品与技术决策

更新时间：2026-08-26

- 分析页与分享海报必须分离：六类分析统一由 `AnalysisShareService` 生成 `AnalysisShareData`，页面负责完整洞察，海报由独立 Renderer 只提炼 5–8 个可验证结论，禁止直接截取分析页面或为填充版面编造内容。
- 分析海报 V1 固定为 1080 × 1440；视觉使用官方北极熊汉堡图标和现有品牌 Token。主视觉按“Visit 实拍 → 餐厅稳定封面 → 合法 Provider 图片 → 菜系兜底”降级，并通过用户、类型和周期生成稳定种子；代表餐厅名称与图片必须用同一个 `restaurantId` 绑定。
- 所有分析分享默认经过严格隐私过滤，不分享邮箱、内部账号 ID、精确私人位置、未授权真实消费或饭搭子私密身份。“换一张照片”只能在当前报告可分享的真实候选池内轮换。
- 分析海报运行时生成且不落数据库；Web 当前生成 PNG 并优先使用系统文件分享，能力不足时保存图片。iOS 后续复用数据契约与隐私结果实现原生 Renderer，本轮不新增分析快照表、海报缓存表或 migration。
- App 启动后首先显示地图；地图与列表采用两个完整模式，地图模式仍保留餐厅分类栏和始终可见的“查看列表”入口。
- “味觉足迹”是列表模式中的独立动态流，不是地图筛选；按 Visit 时间展示笔记与照片，并允许持续滚动浏览。
- 当前位置使用“圆形头像 + 主色外圈 + 小尖角”的定位气泡；餐厅继续使用圆形图片标记，两个体系不混用。
- 全局视觉只使用一套 Token：主品牌色 `#506C8C`、深品牌色 `#344F69`、浅品牌背景 `#EDF2F6`、主文字 `#172A3A`、次文字 `#727C84`、页面背景 `#F7F7F5`、卡片 `#FFFFFF`、分割线 `#E3E6E8`、未选中 `#7C7C78`和低频暖色 `#D09A63`；页面不再各自写死近似蓝灰色。
- 北极熊汉堡是 Taste Map 统一应用图标，同时用于页内品牌标识、favicon、PWA/手机桌面图标和 Windows 启动快捷方式。
- 表单中的可选附加项用明确动作入口表达：菜品直接显示“添加”，饭搭子默认限量展示并通过“更多”展开。
- 所有真正需要提交的长表单统一复用 `StickyFormActionBar`：滚动区与操作栏分离，取消和保存固定在当前 Modal / Sheet / 页面底部，始终可见并保留禁用、保存中和错误状态；短输入、即时保存和浏览页面不机械添加固定底栏。
- “适合场景”描述单次 Visit，允许同时选择多个场景并可自定义；旧单值字段只用于兼容。
- 单次到访不单独管理可见性；用户在“我的”中统一选择仅自己、互相关注或公开。
- 关注关系只在个人页显示“关注我的”和“我关注的”；互相关注作为“我关注的”列表状态，不单独设入口。
- “好友推荐”由独立 `FriendRecommendationService` 统一计算，前端只消费候选、一条首要理由和独立推荐强度；共同好友或已绑定历史饭搭子映射“优先认识”，有足够同味信号或共同餐厅映射“推荐认识”，只有同城等弱信号映射“可以认识”。共同想吃只有在 WantToGo 具备可验证公开范围后才能作为理由，当前不得读取私人收藏。免费与会员使用相同排序，不以会员身份加权；已关注、待处理申请、近期拒绝、自身、不可发现和非测试环境中的测试用户必须在 Service / API 层排除。好友推荐只在顶部“添加好友”的统一页面中展示，与用户搜索共用一个入口，不再作为个人首页模块。
- Premium 汉堡只表达身份，使用无底色、无外框、无文字的小型彩色 SVG，显示在用户名右侧而非头像上；是否显示只由有效会员 Entitlement 决定。
- 所有 Premium 入口必须调用统一的 `openPremiumPaywall(sourceFeatureKey)`，由同一个 Premium 页面根据服务端 Entitlement 切换免费销售态与已开通状态态；页面不得自行写价格、购买按钮或另一套会员中心。免费用户的本人资料只显示“开通 Premium”，会员用户只通过用户名旁可点击的 Burger 进入状态页，设置始终保留“会员与订阅”。入口来源只用于分析和上下文文案，不改变权限结果；免费账号添加第 4 张到访照片时也必须由“继续添加”直接打开同一会员页。
- Premium 状态页按 Entitlement 来源决定操作：App Store 月度/年度订阅可管理订阅；永久会员不展示续订或订阅管理；后台赠送、活动和兑换码只展示对应有效期。购买、恢复、授予、撤销和到期必须通过统一会员变更事件实时刷新，不要求重新加载页面。
- 订阅价格以原生 StoreKit 返回的本地化 `displayPrice` 为唯一展示来源；Web 环境和原生商品不可用时必须显示“暂时无法获取订阅信息”、重试和 iPhone App 提示，不得用硬编码价格冒充真实商品。年度优惠只在月度与年度方案拥有同币种数值价格时计算；已开通账号只展示会员状态、订阅管理和恢复购买，不重复展示购买方案。
- 购买、恢复与管理订阅通过平台无关的 Membership Store Bridge 调用原生能力，结果仍需刷新服务端 Entitlement；客户端购买结果不能直接授予会员。会员到期或撤销只改变权限，不删除既有餐厅、到访、头像或照片，超过免费上限的历史照片保持可读但不能继续超额新增。
- 用户加入时间直接读取既有 `User.createdAt`，统一显示到月份；它是账号资料，不新增第二个“加入时间”字段。
- “我的”页采用个人主页而非数据后台的视觉层级：顶部操作左右分置，头像、昵称、Premium 标识、简介或加入时间及编辑资料居中；随后固定展示带语义图标的“我关注的 / 关注我的 / 去过 / 想吃”四项等宽统计，不展示公开记录，去过和想吃都按唯一餐厅身份去重。好友搜索与推荐统一收进“添加好友”入口；“今天吃什么 / 我的口味档案”继续使用同一行等宽等高入口，再进入回味、食单、洞察和设置。
- “今天吃什么”转盘属于“我的”中的工具模块，不占独立底部导航入口；地图餐厅只加入统一候选池，不自动打开轮盘。
- 转盘候选餐厅属于当前会话临时状态，不写入餐厅/到访数据；最多 10 家。轮盘固定以至少 5 个视觉分区呈现，真实候选才会参与随机，空位只作为“添加更多餐厅”入口；只有用户主动开始才旋转并播放可静音的持续提示音。
- 底部主导航只保留地图、发现和我的；“添加餐厅”作为独立快捷按钮悬在发现入口正上方，不占用导航栏位。
- “发现”的五栏数据逻辑独立：关注看已关注用户；为你推荐只依据自己的历史记录推荐餐厅；同味之选依据口味相似用户；最新按时间；趋势按 7/30 天热度。
- 发现五个分栏的餐厅卡统一复用 `RestaurantQuickActions`：左侧只承载“点赞 / 评论 / 转发”等社交互动，右侧固定为“记录去过 / 想吃 / 加入抽签”。餐厅正文、图片和名称在当前发现上下文打开同一套完整详情；用户头像和昵称只打开用户资料。三项餐厅操作均不得触发卡片详情、切换地图或自动打开轮盘，关闭详情和到访表单后恢复原分栏与滚动位置。当前社交互动状态仅保存在 Web 本地，不伪装成已经跨用户、跨设备同步的数据，待统一社交 API 完成后再升级存储方式。
- 发现页分享的对象始终是 Restaurant，而不是 Visit、用户、地图或推荐理由。分享链接只使用不可反推内部 ID 的公开餐厅标识与固定 `ref=discover_share`，优先系统分享、降级复制链接；公开页和分享文本只输出经过白名单筛选的餐厅字段与达到样本阈值的公开评分，取消分享不报错，分享计数不在 UI 展示。
- “为你推荐”的解释必须指向用户曾吃过的具体相似餐厅并给出相似百分比，不能用笼统的“经常给某菜系高分”。
- “为你推荐”和地图推荐的距离筛选支持 1/3/5/10 公里和按最近排序。设备城市与浏览城市一致时使用设备位置；跨城市或无定位权限时改用当前浏览城市候选中心并明确显示锚点，禁止静默使用异地 GPS。距离、评分属于硬筛选，系统只建议最小有效放宽，必须由用户点击后才改变条件；排序不计入筛选数量，也不得减少候选。
- 推荐空状态统一区分筛选归零、推荐证据不足、无公开内容、无关注动态与趋势样本不足；筛选归零由运行时 Filter Result Resolution 从同一候选池分析原因和放宽建议，不持久化、不新增数据库字段。
- 测试发现数据只允许写入 Development 本地 D1；Production 不自动生成、复制或清理测试用户。
- 当前账号的跨城市已到访测试餐厅只通过 Development 本地种子增量添加；杭州基准数据保留不动，上海、北京、广州、深圳、成都、南京、苏州和香港各补 2 家。任何同类测试数据都不得进入或覆盖 Production。
- Development 的个人云同步与公开社交读取必须分成两个开关：个人 `food-map-dev` 不自动拉取 D1 餐厅/Visit，Social API 可以继续读取公开测试用户和发现内容；公开样本绝不能因社交测试而进入当前用户的个人去过清单。
- 餐厅社交评分按用户等权：先计算每个用户在同一餐厅的个人平均，再计算全部用户、好友和口味相似人群平均；当前餐厅详情不展示重复到访率。
- 餐厅评分参考固定为历史预测、全部用户、好友评分和同味评分四项：大圆显示分数，小圆显示历史餐厅样本数或参与用户数；历史预测动态使用本地有效评分、菜系标签、价位、城市与重复到访相似度计算，不写入数据库、不伪造无样本分数。
- 餐厅详情保留三枚明确快捷动作“去过 / 想吃 / 抽签”，并放在店名右侧以节省纵向空间；信息顺序固定为评分参考、用户实拍、我的到访概览、到访历史。公开发现记录中的实拍必须进入同一详情的用户实拍区，不能只在发现卡片出现。
- 评分参考的大圆按 10 分制评分色阶显示；小圆只显示数字样本量，不追加“家/人”。无数据时圆内只显示统一空状态图案与“暂无数据”，不在圆外重复说明。
- 去过餐厅的顶部信息必须明确显示当前用户自己的 10 分制评价；个人评价与全部用户、好友、同味评分保持独立层级。
- “附近餐厅”必须来自浏览器高精度 GPS，并先转换为高德坐标，再并行使用多个餐饮关键词检索 3 公里范围、去重并按真实距离排序；没有可靠定位时不使用城市级结果冒充附近结果。
- 地图列表、发现页点击餐厅都在当前上下文展示完整餐厅信息，不通过切回地图表达详情；移动端详情覆盖地图内容。
- 个人资料、头像和地图隐私收进同一个“编辑资料与隐私”面板；关注管理与用户发现分开呈现。
- 免费用户可使用全部预设头像；只有服务端确认的会员可上传自定义头像，客户端不能自行提升会员等级。
- 个人页和饭搭子分析中的头像统一使用固定圆形细黑线，不用随机或按用户变化的彩色描边。
- Web 仍是当前主要客户端，但数据模型、同步接口、认证与图片引用不得绑定到特定 Web UI，以便未来 iOS 复用。
- 只有字段、数据库结构或同步协议变化时才检查 migration；纯 UI、布局、颜色和文案修改跳过数据链路检查。
- Restaurant 的跨平台身份由 Global Restaurant ID / Provider 映射服务维护；地图 SDK 的 POI ID 只是来源标识，不能成为所有业务模型的唯一真值。
- 同步采用 local-first：本地写入先成功，随后由幂等操作队列增量上云；图片只同步元数据和存储引用，不把二进制写入 D1。
- 会员能力以服务端有效 Entitlement 为准；前端开关和本地字段不能直接授予会员权限，管理员变更必须留下审计记录。
- Development 的当前测试账号固定授予终身会员能力，用于完整功能验收；另设本地身份 `free-tester` 对应的非会员测试账号。测试身份通过本地启动参数和仅限 localhost 的请求头传递，Worker 仍是会员真值来源；线上环境忽略这套本地测试身份。
- 会员与非会员测试数据必须双重隔离：会员测试版继续使用 `food-map-dev`，非会员测试版使用 `food-map-dev-free`，Production 始终使用稳定的 `food-map-prod`。不得为了切换会员状态复制、清空或重命名正式数据库。
- 非会员测试数据使用版本化固定种子 `TASTE_MAP_TEST_SEED`，仅在非会员 Development 数据库内按种子版本重建；测试内容必须丰富到可验证免费推荐、到访、想吃、饭搭子、推荐来源和食单，但不得为了测试向 Production 写入或从会员测试库复制真实数据。
- Premium Badge 是会员身份提示，不代表评分、权威或管理权限；使用统一汉堡矢量图标和品牌蓝，只在有效 Entitlement 为会员时显示。所有头像位置复用 `UserAvatar`，会员授予/撤销通过统一事件刷新，页面不得根据用户名、邮箱或本地开关猜测会员状态。
- 免费推荐只提供基础个性化结果；会员深度推荐才开放多条完整解释、高级推荐筛选和同味之选。照片上限、完整口味档案、饭搭子分析、推荐来源分析和自定义头像统一调用同一会员策略，不允许各页面自行写一套会员判断。
- 推荐适配度由统一 Recommendation Service 输出语义枚举：`STRONG_MATCH`、`GOOD_MATCH`、`MODERATE_MATCH`、`EXPLORATION`；前端只映射为“优先推荐 / 推荐给你 / 可以试试 / 换个口味”，不得根据原始分数自行推断，也不得显示“推荐 8.7”一类伪评分。匹配等级与证据置信度是两个独立概念；公开用户评分继续复用 0、1–4、5–9、10+ 独立用户样本的置信度规则。
- 推荐核心理由必须默认可见，不允许先折叠再让用户点击理解推荐。Premium 主卡显示 2–3 条最高价值的个性证据，免费版显示 1 条基础依据；“查看完整分析”只承载次级证据，注意项最多一条。当前城市、附近、地址和泛化高分等低价值信息不得作为主理由。推荐卡右下固定为详情、想吃、抽签三枚同尺寸 44px 纯图标操作，并提供可访问名称与选中状态。探索位目标约为 20%，但仍必须通过明确硬筛选和最低质量门槛。
- 推荐卡图片只使用当前餐厅真实存在的商家图、公开到访图或已同步照片，按稳定顺序去重后最多显示 3 张；没有足够真实图片时宁可显示 1–2 张，也不复制同一张或注入假图补位。
- 评分允许缺省；所有可编辑星级统一复用 `StarRating`，取值为 `null` 或 0.5—5 星。每颗星拥有独立 44px 命中区，左半为半星、右半为整星，指针坐标只相对当前星计算，并保留键盘半星步进与纵向触摸滚动；存储不得使用整数取整，展示和统计统一换算为 10 分制。
- 推荐、口味档案、餐厅统计和月报/年报共享“有效 Visit”口径；重复同步、软删除和未评分记录按各指标定义排除。
- 完整口味档案是由现有 Restaurant / Visit 动态生成的私有分析报告，不新增统计快照字段；页面固定覆盖结论、成熟度、菜系、预算、体验偏好、场景、用餐方式、复购、评分风格、来源和近期变化，避免在多个组件重复实现口味算法。
- 个性化推荐只依据当前用户的历史偏好；同味推荐才使用相似用户行为；数据不足必须显示真实降级原因，不能伪造推荐或 0 分。
- 食单是独立的内容组织实体，不等同于想吃；公开食单使用 `#list=<id>` 稳定地址，服务端按 private/friends/public 校验读取权限。
- 食单、地图列表和发现页的餐厅点击都在当前上下文打开同一套完整餐厅详情；关闭详情恢复来源页面、原食单及原来的发现分栏。
- 本人页面保持个人仪表盘，展示实际简介或加入时间，顶部统计固定为“我关注的 / 关注我的 / 去过餐厅 / 想去餐厅”，不展示“公开记录”。他人公开主页采用“身份与关系操作 → 关注/粉丝/去过餐厅/想去餐厅 → 单一动态/口味/食单导航 → 可选共同想吃 → 代表餐厅 → 轻量地图足迹 → 最近公开到访”的层级；想去只通过顶部统计进入，地图不再作为重复一级导航。代表餐厅按 Restaurant 聚合，最近动态按 Visit 展开，本月回顾、年度回顾和个人分析只属于本人页面。
- 从发现页进入他人主页时必须记录来源分栏和滚动位置；返回应等待发现内容恢复后再定位，避免异步加载导致跳回顶部。
- 月报、年鉴和那年今日动态计算，不复制保存一份容易过期的统计结果。月报优先当月高光、模式与有意义的环比，年鉴用全年关键餐厅、口味变化、实际到访城市和有意义的同比讲故事；单次到访不生成虚假趋势。那年今日只展示真实的往年同日记录。对外分享必须使用去隐私摘要，默认不包含真实支出、饭搭子、推荐来源或私人照片。
- 回顾系统的图片固定按“当次到访实拍 → 餐厅稳定封面 → 商家 Provider 图 → 占位图”选择，不随机更换；当月高光综合评分、实拍、笔记、重复到访、首访、饭搭子、里程碑和时间新鲜度，但只呈现可由真实记录证明的结论。
- 回顾消费只使用当前用户实际支出 `myActualSpend`，不得使用聚餐总价 `totalPrice` 伪装个人消费。覆盖率低于 60% 隐藏金额，60%–99% 只表达“已记录”，只有 100% 可使用“总计”。本月回顾与年度年鉴属于 Premium，那年今日属于免费回忆入口。
- 饭搭子分析的事实来源默认仅为当前用户自己的 Visit：消费只统计 `myActualSpend`，评分只描述“和 TA 一起时我的评分”，绑定用户在没有明确可见权限时也不读取其 Visit 或 TasteProfile；解绑只移除账号关联，不删除历史饭搭子和到访。
- 饭搭子洞察统一按共同 Visit 数量分级：0–2 次仅显示事实总览，3–5 次允许基础分析，6 次以上才显示完整关系洞察；页面不得把普通饭搭子包装为排行榜、共同评分或关系强弱判断。
- 饭搭子分析采用“关系摘要 → 可搜索列表 → 单人完整洞察”的信息层级；图标用于帮助快速识别次数、餐厅、日期、消费、菜系、城市和共同记忆，但不改变统计口径。
- 饭搭子身份展示统一由 `companionInsights` 解析：已绑定用户优先使用真实账号头像，其次使用饭搭子自己的可选私人头像，再识别家人/同事/朋友等类别型饭搭子，普通文字名称则由稳定 `companionId` 生成可读文字头像和固定主题，最后才使用占位图；同一饭搭子不得因刷新或排序改变头像。未绑定账号的饭搭子允许编辑名称、私人头像和关系备注，改名必须同步兼容旧 Visit 文本并保留 companionId。列表语义固定为：全部按共同次数降序、最近按最近共同到访降序且空日期置后、常一起按次数降序并以最近日期破同分、历史饭搭子为至少 3 次且超过 90 天未共同到访。阈值集中在统一配置，搜索与当前模式叠加，不持久化分析结果。
- 推荐来源按 Restaurant acquisition source 归因：同一餐厅只归入最早一条带来源的有效 Visit，一家餐厅只贡献一个推荐样本；后续 Visit 仅用于该餐厅的个人平均评分、重复到访和实际消费结果验证。历史来源缺失保持未知，不从笔记或平台信息猜测。
- 推荐来源分析是当前用户私有的结果检验，不生成来源的全局“可靠度”；Taste Map 自己的推荐与好友、平台和自行发现使用同一口径。来源表现可以形成受样本置信度控制的弱推荐信号，但不能凌驾于预算、距离、场景、营业状态和长期 TasteProfile。
- 推荐来源“最坑”是从当前用户的真实到访结果动态派生的个人洞察，不写入数据库，也不代表公共评价。候选来源至少需要 6 家独立有评分餐厅，10 家起视为稳定样本；同店多次 Visit 先汇总成一个餐厅结果，重复到访只作为次级信号。没有来源达到门槛时整个“最坑”结论必须隐藏，不能显示空卡或用小样本硬凑。页面、详情和分享均使用来源当前真实名称，人物来源不得匿名化为泛称。
- 饭搭子分析采用参考图确认的信息层级，但事实边界保持不变；推荐来源分析固定使用“结论、分组来源、系统表现、成功证据”四层结构，视觉丰富度不得通过虚构对方私密数据或不存在的推荐结果获得。
- 添加餐厅选中 POI 后，去过与想吃必须复用同一个完整商家信息区，包括商家图、地址、参考价格、电话、营业时间、路线、去过/想吃/抽签、评分参考和用户实拍；状态差异只体现在后续表单。想吃只记录计划所需字段，去过才展开完整 Visit 内容，避免两套页面继续漂移。
- “写下这家餐厅”的结构顺序是组件契约，不能依赖 CSS `order`、绝对定位或两套状态页面仿造：`RestaurantSummarySection` 必须在 `VisitModeSelector` 之前无条件渲染，评分参考和用户实拍属于摘要内部，选择器只控制后续表单。用户实拍只读取到访/公开实拍，与商家主图及“地图上的样子”设置保持分离。
- 餐厅详情不得以“第一个匹配记录”为最终资料；同一 POI/同店命中多条记录时必须合并所有匹配项，让完整资料补齐精简 DTO。餐厅详情和记录/编辑页统一复用 `RestaurantRecordSummary`，电话和营业时间仅在有可靠数据时展示，路线入口始终保留，避免各入口继续维护不同头部。
- 饭搭子分析与推荐来源分析属于完整洞察页，在桌面端使用宽版容器和可读字号；窄屏再响应式收为单列，不能为了复用普通弹窗而把摘要、列表和证据压缩到不可读。
- 他人主页和公开地图必须先在 Worker / Service 层按查看者身份过滤 Visit，再交给前端展示：本人可见自己的有效记录；已接受好友可见 `public + friends`；陌生人只可见 `public`；地图关闭或设为 `private` 时他人不可见，设为 `friends` 时仅已接受好友可见。公开地图按餐厅聚合为一店一标，城市数量和默认城市也只能由过滤后的可见记录计算。
- 外部餐厅 URL、平台 POI ID 和分享文本只作为 Global Restaurant Identity 的识别证据，不能成为新的 Restaurant 主键；成功导入仍复用现有 Restaurant / Provider 映射和用户确认流程，不保存第三方评分、评论或照片。
- 外部链接解析统一使用 `ExternalRestaurantLinkResolver`：高置信唯一候选可直接进入确认，多候选必须由用户选择，中低置信度只回填搜索，`NONE` 明确报错；任何等级都不得静默创建、标记去过或加入想吃。
- iOS Share Extension 只负责接收 URL/文本并写入 App Group 的短期待处理记录；深链只携带不可预测的 `importId`，不携带原始链接、用户文本或认证令牌。主 App 在验证当前账号归属后才调用经过身份验证的解析 API，并复用同一确认界面。
- 外部网页抓取属于服务端受限能力：只允许 HTTPS，拒绝本机、私网与云元数据地址，每次重定向都重新校验目标，并设置跳转次数、超时、响应体和内容类型上限；客户端不得绕过 Worker 直接抓取任意网页。
- Restaurant / Visit 的创建入口统一使用纯 `+` 图标并由 `PlusAction` 承载明确动作：`ADD_RESTAURANT` 只用于全局搜索与添加餐厅，`ADD_VISIT` 只用于已知餐厅并直接新增到访。到访 `+` 是可重复执行的动作，不是去过状态开关，也不显示到访次数；想吃、抽签、分享、点赞、评论和添加好友不得复用该语义。
